# SSTI（服务端模板注入）Writeup

> 场景目录：`html/ssti/` · 机读 PoC：`pocs/vulnlab-ssti-template-injection.yaml`
> CI 断言：7 条（见 `tests/verify_lab.py`）

---

## 一、原理：把用户输入的「数据」当成了「代码」

SSTI 和 SQL 注入、命令注入属于同一个家族 ——
**用户输入被放进了本该是代码的位置**。

区别在于「放进代码」这个动作有多显眼：

| 场景 | 漏洞代码长什么样 | 显眼程度 |
|---|---|---|
| SQL 注入 | `"... WHERE id = " . $_GET['id']` | 能看到拼接 |
| 命令注入 | `shell_exec("ping " . $_GET['ip'])` | 能看到拼接 |
| 文件包含 | `include $_GET['page']` | 能看到直接使用 |
| **SSTI** | `eval('return ' . $expr . ';')` | **一行，看不出问题** |

SSTI 的特殊之处在于：它通常出现在**自己手写的模板引擎**里。

### 1.1 一个非常正当的需求

运营需要能编辑通知文案，里面可以插入动态值：

```
您好，您的订单金额为 {{ 199 * 2 }} 元，请及时支付。
```

实现思路看起来顺理成章 —— 用正则找到 `{{ }}`，把里面的内容当表达式算出来：

```php
$rendered = preg_replace_callback('/\{\{\s*(.+?)\s*\}\}/s', function ($m) {
    return eval('return ' . $m[1] . ';');
}, $template);
```

**整个实现只有一行。** 它没有拼接、没有执行命令、没有文件操作。

### 1.2 问题出在「表达式」这个词的边界上

开发者心里的「表达式」是：

```
199 * 2
```

而 PHP 里的「表达式」是：

```
199 * 2
phpinfo()
file_get_contents('/etc/passwd')
system('whoami')
`whoami`
...（PHP 有上万个函数，这个列表还在增长）
```

**两者是同一个语法类别 —— 没有任何语法规则能把它们分开。**

这就是 SSTI 的修复方向为什么不在「过滤」上：

> 你要过滤的不是「攻击者的写法」，
> 而是「PHP 有多少种表达同一个能力的方式」——
> 这是一份无限长的清单。

### 1.3 从 `49` 到 `whoami` 之间没有门槛

```
{{ 7*7 }}                  →  49            看起来完全符合预期
{{ phpinfo() }}            →  整页环境信息   已经越界了
{{ file_get_contents(..) }} →  任意文件读取
{{ system('id') }}         →  任意命令执行
```

这四步用的是**同一个机制**，中间没有任何额外的突破动作。

**所以 SSTI 一旦成立，通常直接等同于 RCE** —— 不存在「轻微 SSTI」这种说法。

## 二、low 档：表达式直接求值

### 2.1 漏洞代码

```php
// template.php
function ssti_render(string $template, callable $evaluate): string
{
    return preg_replace_callback('/\{\{\s*(.+?)\s*\}\}/s',
        fn($m) => $evaluate($m[1]), $template);
}

// low.php
$rendered = ssti_render($template, fn($expr) => ssti_eval_unsafe($expr));

// ssti_eval_unsafe()
ob_start();
$value = @eval('return ' . $expr . ';');
$printed = ob_get_clean();
```

> 实现里用 `ob_start()` 包住 eval，是为了同时照顾两种执行方式：
>
> - `system()` / `passthru()` 这类函数是**直接打印**结果的，返回值只是最后一行
> - 反引号 `` `cmd` `` 等价于 `shell_exec()`，它是**返回**结果的
>
> 不捕获的话，前者的输出会跑到页面 HTML 结构外面，
> 使用者会以为「payload 没生效」，其实已经执行了。

### 2.2 利用

**第一步：确认表达式确实在执行**

```
{{ 7*7 }}   →  49
```

这一步比直接读文件更能说明问题的性质 ——
它证明 `{{ }}` 里的内容被当成了**代码**，而不是**数据**。

**第二步：调用函数读文件**

```
{{ file_get_contents('ssti_probe.txt') }}
```

`file_get_contents(...)` 就是一个普通的 PHP 表达式，
所以**不需要任何特殊技巧** —— 这就是全部攻击。

**顺带：执行命令**

```
{{ `echo VULNLAB_SSTI_CMD_MARKER` }}      反引号运算符
{{ system('echo VULNLAB_SSTI_CMD_MARKER') }}
```

### 2.3 一个关于判据的细节

本档的判据（以及 PoC 里的 matcher）都限定在**「渲染结果」那个区块**里，
而不是全文搜标记串。

原因：靶场页面会把提交的模板原样回显到输入框里，
而标记串就是我们 payload 的一部分 —— **它必然出现在页面上**。
全文匹配会无条件命中。

> 这和命令注入场景「判据限定在命令输出区块内」、
> XXE 场景「判据限定在订单号字段内」是同一个思路：
> **排除「检测特征被检测行为本身制造出来」的可能。**

## 三、medium 档：黑名单挡住括号

### 3.1 防护措施

```php
foreach (['(', ')'] as $bad) {
    if (strpos($expr, $bad) !== false) {
        return '[已被过滤]';
    }
}
return eval('return ' . $expr . ';');
```

### 3.2 这个防护的思路是对的

它抓到了一个真实的规律：

> **PHP 里调用函数的写法是 `func(...)` —— 括号是必需的。**

于是推理链看起来成立：

```
不许出现括号  ⟹  不许调用函数  ⟹  SSTI 被堵住
```

**第一段是对的。第二段是错的。**

### 3.3 绕过：反引号运算符

PHP 的**运算符**列表里有一个能执行命令的：

```php
`command`
```

它等价于 `shell_exec('command')` —— 执行一段 shell 命令**并返回输出**。
整个写法里**没有一个括号**。

```
{{ `echo VULNLAB_SSTI_CMD_MARKER` }}
```

表达式里既没有 `(` 也没有 `)`，黑名单放行，而 `eval` 照样把它送进了 shell。

> 顺带一提：`shell_exec` 这类函数在很多主机上被 `disable_functions` 禁掉，
> 但**反引号运算符走的是同一个底层函数** —— 如果 `disabled_functions`
> 里写的是 `shell_exec`，反引号同样会被禁；
> 如果没禁，那两者都能用。**它不是绕过 `disable_functions` 的手段**，
> 它绕过的是**基于文本的黑名单**。

### 3.4 这一档和前面几次「黑名单绕过」是同一个结构

| 场景 | 防护想禁止的能力 | 它抓的特征 | 绕过方式 |
|---|---|---|---|
| SQL 注入 | 做联合查询 | `union` | 双写 `ununionion` |
| 文件包含 | 穿越目录 | `../` | 双写 `....//` |
| 反序列化 | 实例化危险类 | `Cache` | 小写 `cache` |
| **SSTI** | **调用函数** | **`(` `)`** | **反引号 `` `cmd` ``** |

四行省略号里是同一件事：

> **黑名单在列「特征」，而「特征」和「能力」之间永远是**多对多**的。**

防护者能想到的是「最常见的那一种写法」，而语言里表达同一个能力的写法
往往不止一种 —— 而这些等价写法不会都带同一个特征。

## 四、high 档：不做表达式求值

### 4.1 修复代码

```php
// ① 语法收窄 —— 必须是一个合法的变量名
if (preg_match('/^[a-z_][a-z0-9_]*$/', $expr) !== 1) { /* 拒绝 */ }

// ② 白名单查表 —— 表里没有就拒绝
if (!array_key_exists($expr, SSTI_ALLOWED_VARS)) { /* 拒绝 */ }

// ③ 没有 eval —— 整个文件里不存在「执行这个字符串」这一步
return (string) SSTI_ALLOWED_VARS[$expr];
```

`SSTI_ALLOWED_VARS` 里全是字符串和数字：

```php
const SSTI_ALLOWED_VARS = [
    'product' => '示例商品',
    'price'   => '199',
    'total'   => '398',
    ...
];
```

### 4.2 三层各自在做什么

| 层 | 作用 | 为什么需要它 |
|---|---|---|
| ① | 语法收窄 | `7*7`、`system('id')`、`` `cmd` `` 连格式都不合法 |
| ② | 白名单查表 | 合法标识符也可能指向不存在的东西 |
| ③ | **没有 eval** | **取消了整个攻击面** |

第 ③ 点是本档的核心：**前两档都是「先执行，再想办法过滤」，
这一档干脆没有「执行」这个动作。**

于是也就不存在「绕过过滤」这件事 —— 因为没有任何东西会被执行。

### 4.3 白名单和黑名单的本质差别

这是本靶场反复出现的主题，在 SSTI 场景里体现得最清楚：

| | 黑名单 | 白名单 |
|---|---|---|
| 问的问题 | 「这个输入危险吗」 | 「这个输入在我允许的列表里吗」 |
| 需要枚举 | **所有危险的写法** | **我自己需要的东西** |
| 完整性 | 无法保证 | **可以保证** |

`SSTI_ALLOWED_VARS` 只有 5 个键。**检查它是否完整，是一个可以在 10 秒内完成的事。**
而「PHP 有多少个可以用来读文件/执行命令的写法」，这个问题没有答案。

### 4.4 代价：模板里不能写计算了

本档的做法有个明显的代价 —— `{{ 199 * 2 }}` 不能用了。

这是**真实的取舍**，必须说清楚：

| 业务需求 | 正确做法 |
|---|---|
| 只需要插入动态值 | 变量替换（本档的做法） |
| 需要动态计算 | 把计算放在**服务端代码里**，模板只取值 |
| 确实需要用户写表达式 | 用成熟引擎的**沙箱模式**（如 Twig SandboxExtension） |

**没有「既让用户写任意表达式，又保证安全」这个选项。**
如果有人说有，那多半是还没被找到绕过方法而已。

### 4.5 第一条建议其实是「别自己写模板引擎」

模板引擎不是一个下午能写完的十几行正则。

成熟引擎（Twig / Smarty / Blade）默认就有沙箱、有转义、有明确的设计边界，
它们踩过的坑比一个人能想出来的多得多。

**SSTI 之所以经常出现在自研引擎上，正是因为它「看起来很简单」。**

## 五、其他值得知道的手法

### 5.1 不是只有 `{{ }}` 才有问题

不同模板语法的注入点各不相同：

| 引擎 / 语法 | 典型 payload |
|---|---|
| Twig / Jinja2 | `{{7*7}}`、`{{_self.env.registerUndefinedFilterCallback("system")}}` |
| Smarty | `{$smarty.version}`、`{php}...{/php}` |
| Velocity | `#set($x=...)` |
| Freemarker | `<#assign x="freemarker.template.utility.Execute"?new()>` |
| 自研 | 取决于它自己定义的语法 |

**判断有没有 SSTI，先看「用户输入会不会进入模板」，
再看「这个模板引擎叫什么、版本多少」** —— 后者决定了 payload 怎么写。

### 5.2 模板注入的入口常常很隐蔽

不一定只有「模板编辑框」才是入口：

| 看似无害的功能 | 为什么可能成为入口 |
|---|---|
| 邮件/通知模板 | 最典型 |
| 「自定义列名 / 表头」 | 如果服务端用模板渲染它 |
| 「文件导出的文件名」 | 有些导出组件会用模板拼文件名 |
| 用户昵称 | 如果欢迎语是用模板渲染的 |
| 错误信息里带用户输入 | 某些框架会用模板渲染报错页 |

**关键在于「服务端有没有把这段文本当模板编译」**，
而不是「这个字段看起来像不像模板」。

### 5.3 客户端模板 ≠ 服务端模板

Vue / React 的 `{{ }}` 是在浏览器里渲染的 —— 那是 XSS 的领域，不是 SSTI。

区分的办法：**看这段模板文本有没有被送到服务端**。
如果它只在浏览器里被处理，那最多是 XSS；
如果服务端会编译它，那就是 SSTI（通常更严重）。

### 5.4 与代码注入的区别

| | SSTI | 代码注入 |
|---|---|---|
| 用户输入进入的位置 | 模板表达式 | 直接进入 `eval` / `include` |
| 表现形式 | `{{7*7}}` → 49 | 直接传 PHP 代码 |
| 共同点 | **都是「数据被当成代码执行」** | 同左 |

**SSTI 本质上是代码注入的一种**，只是包装成了「模板引擎」这个看起来更无辜的东西。

## 六、防御清单

| 优先级 | 做法 | 说明 |
|---|---|---|
| **①** | **别自己写模板引擎** | 用 Twig / Smarty 等成熟引擎 |
| **①** | **不要 `eval`** | 「不执行用户输入」是最彻底的修复 |
| **①** | **模板文本只来自开发者** | 用户只能提供**数据**，不能提供模板 |
| **②** | 变量白名单 | 只允许引用预定义的值 |
| **②** | 需要表达式时用沙箱模式 | Twig SandboxExtension 把「允许调用什么」做成显式清单 |
| **③** | 语法收窄 | 允许的字符集越小越好 |
| ❌ | **只过滤括号 / 只过滤 `system`** | **本档 medium 就是为了说明这条不够** |

按有效性排序：**① ≫ ② > ③ ≫ ❌**。

最后一行需要强调：

> **过滤是在缩小攻击面，不是取消攻击面。**
>
> 而一旦 SSTI 成立，它的能力上限就是 RCE ——
> 缩小后的攻击面依然是 RCE，只是 payload 需要更长一点。

## 七、和本靶场其他场景的联系

### 7.1 「数据被当成了代码」的三种形态

| 场景 | 数据被放进了 | 结果 |
|---|---|---|
| SQL 注入 | SQL 语句的语法位置 | 能读任意数据 |
| 命令注入 | shell 命令 | 能执行任意命令 |
| **SSTI** | **模板表达式** | **能执行任意命令（更直接）** |

三者的修复方向完全一致：

> **把数据和代码分开 —— 而不是「让数据看起来不像代码」。**

SQL 用参数化查询（数据永远不参与语法解析），
命令注入用 `escapeshellarg` + 白名单（数据被引号包住，不参与解析），
SSTI 用变量替换（根本不执行）。

**这三条路径在根本上是一样的：让数据待在数据的位置上。**

### 7.2 与 LFI / 反序列化的联系：RCE 的三条不同路径

| 场景 | 怎么走到代码执行 |
|---|---|
| 命令注入 | 直接往 shell 里塞命令 |
| 文件包含 | 包含一个自己能控制的文件（或 `php://input`） |
| 反序列化 | 用现有的类拼出一条链 |
| **SSTI** | **写一个表达式** |

四条路径的共同点：**它们都不是「注入了一段代码」，而是「让服务端去执行已有的能力」。**

反序列化最典型 —— 代码里一个 `eval` 都没有，却能 RCE。
**这就是为什么「我的代码里没有 eval」不能作为「不会被 RCE」的理由。**

### 7.3 与 CSRF / JWT 的联系：可信输入的边界

这三个场景（SSTI / JWT / CSRF）都在讨论「什么输入可以被信任」：

| | 不可信的输入 | 正确做法 |
|---|---|---|
| SSTI | 模板表达式 | 只接受变量名，查白名单 |
| JWT | `alg` 字段 | 服务端决定算法，不听 token 的 |
| CSRF | `Referer` | 用服务端生成的 token |

**共同点：凡是「请求方可以自由决定的」，都不能作为安全判断的依据。**
