# 越权（水平越权 / IDOR）Writeup

场景目录：`html/idor/` · 机读 PoC：`pocs/vulnlab-idor-broken-access-control.yaml`
CI 断言：8 条（见 `tests/verify_lab.py`）

---

## 一、原理：这个场景和前面九个都不一样

前面九个场景里，攻击者做的每一件事都是**服务端不希望他做的**：
注入 SQL、执行命令、读任意文件、伪造签名、去掉 Referer……

越权不是这种形态。在这个场景里，攻击者做的每一件事
**都是系统正常提供的功能**：

```
访问 /idor/low.php?order_id=1003
        ↓
系统正常地查询、正常地返回订单、正常地渲染页面
```

**没有任何一行代码被绕过，也没有任何过滤被绕过。**
问题在于：系统压根没打算区分「这个订单是谁的」。

### 1.1 认证 vs 授权

这两个词经常被混着用，但它们是两件事：

| | 认证（Authentication） | 授权（Authorization） |
|---|---|---|
| 回答的问题 | **你是谁？** | **你能做什么？** |
| 实现方式 | 密码、token、会话 | 权限判断、归属校验 |
| 失败表现 | 登录不上 | **能读到不该读的数据** |
| 出错时的现象 | 用户会立刻发现 | **没有任何异常，功能「正常」** |

越权漏洞属于后者。而它的可怕之处正在最后一行：

**忘了做授权，不会报错、不会抛异常、单测也测不出来，因为功能在「正常」工作。**

一个没有归属校验的订单接口，测试用例会愉快地通过：
「查询订单 1001 返回订单 1001」✓ —— 用例里没有「用 bob 的身份查 alice 的订单」这一条。

### 1.2 为什么 OWASP Top 10 把它排在第一

A01:2021 就是「失效的访问控制」。它排第一有两个很实际的原因：

**① 自动化扫描器很难发现它**

扫描器不知道「1003 号订单该属于谁」——
没有 SQL 报错、没有异常响应、没有可识别的特征。
它需要**理解业务语义**才能判断，而这正是工具做不到的。

**② 它的形态极其多样**

换个参数名、换个接口、换个 HTTP 方法，就可能是一个新的越权点。
**没有「一种通用的绕过写法」可以套用。**

这两点合起来意味着：

**越权只能靠人工测，而且必须理解业务。**
也正因为如此，它是最值得花时间的一类漏洞。

### 1.3 越权的三种形态

| 类型 | 含义 | 本场景 |
|---|---|---|
| **水平越权** | 同级用户之间互相访问数据（A 看 B 的订单） | ✓ 本档演示的 |
| **垂直越权** | 低权限用户执行高权限操作（普通用户调管理员接口） | 机制相同，见 §5.2 |
| **上下文越权** | 执行了业务上不该允许的操作（越过分页上限、跳步审批） | 见 §5.3 |

水平越权还有个更常见的名字：**IDOR**（Insecure Direct Object Reference，
不安全的直接对象引用）—— 指「用 ID 直接引用对象，而不校验归属」。

## 二、low 档：没有归属校验

### 2.1 漏洞代码

```php
// low.php
$order = idor_find_order($orderId, null);
//                        ↑ 第二个参数是 ownerUid，传 null = 不做归属过滤

// 等价的 SQL：
//   SELECT * FROM orders WHERE id = ?
```

对比一下 high 档：

```php
// high.php
$order = idor_find_order($orderId, $sessionUid);
//                                   ↑ 来自服务端会话

//   SELECT * FROM orders WHERE id = ? AND user_id = ?
```

**差别就是一个 WHERE 条件。**

### 2.2 利用

```
GET /idor/low.php?order_id=1001   → alice 自己的订单（正常）
GET /idor/low.php?order_id=1003   → bob 的订单，备注里有通关凭证
GET /idor/low.php?order_id=1004   → carol 的订单
```

订单号是连续的数字 —— 真实系统里通常就是这样（自增主键、可预测的流水号）。
但只要知道一个别人的 ID，甚至不需要枚举，就能读到。

### 2.3 值得单独说的一点

**这行代码本身没有任何「错误」。**

```php
SELECT * FROM orders WHERE id = ?
```

按主键查一条记录，是完全正常、完全标准的写法。
它不缺少引号、没有拼接、没有类型问题 —— **没有任何一个代码检查工具会报它。**

缺的是那个**业务上必须存在**的约束。

这也是为什么「代码质量高」和「没有越权漏洞」是两件不同的事：
前者是语法和结构层面的，后者需要对**业务语义**做判断。
「这个订单该不该让这个人看」这个问题，只有人知道答案。

## 三、medium 档：校验了，但依据来自客户端

### 3.1 防护措施

```php
// 加了归属条件 —— 这一行是对的
$order = idor_find_order($orderId, $effectiveUid);
//   SELECT * FROM orders WHERE id = ? AND user_id = ?

// 但第二个问号填的是这个：
$uid = (int) $_REQUEST['uid'];   // ← 从请求里读「我是谁」
```

### 3.2 「看起来已经修好了」

从 SQL 的角度看，防护确实到位了 —— 不是本人查不到。

```
?order_id=1003              → 拒绝（uid 回落成 alice，订单不是她的）
?order_id=1003&uid=3        → ★ 拿到了 bob 的凭证
```

把 `uid` 改成 3，就变成了 bob。

### 3.3 这个漏洞的形状需要单独记住

前九个场景里，漏洞都是「某个检查被绕过了」。
这一档不是 —— **检查没有被绕过，它通过了。**

```php
if ($order['uid'] === $uid)   // 3 === 3 → 通过
```

校验逻辑没有任何问题。出问题的是**输入给校验的那个值从哪来**。

概括成一句：**校验的正确性，取决于它所依据的那个信息的可信度。**
依据一个客户端能随意设置的值去做权限判断，等于没有做权限判断，
只是多写了几行代码。

### 3.4 这个错误在真实项目里长什么样

它不总是 `uid` 这个参数名。常见形态：

| 形态 | 为什么危险 |
|---|---|
| `X-User-Id` 这类网关注入的请求头 | 直连应用服务器时可以自己填；或者网关配置有疏漏 |
| 客户端传来的 `user_id` / `account` / `tenant_id` | 直接就是客户端可控 |
| Cookie 里的「明文身份」（没有签名） | 客户端可改 |
| **JWT 里未经验证的字段**（没校验签名就读 `sub`） | 那个字段只是 base64url，谁都能改 |

最后一条需要展开：**用 JWT 传身份本身不是问题，未校验签名就读它才是问题。**
这正是 JWT 场景（`html/jwt/`）演示的内容 —— 两个场景在这里接上了。

### 3.5 判断标准

有一个非常简单的判据：

**这个值在不在请求里？在，就不能用来做权限判断。**

按这个标准检查一遍代码里所有「和身份有关的变量」，
能把这一类漏洞基本上扫干净。

## 四、high 档：四层防护

### 4.1 修复代码

```php
// ① 身份只从服务端取 —— 请求里根本没有这个信息
$sessionUid = CURRENT_UID;          // 真实项目：$_SESSION['uid']

// ② 归属条件写进查询本身
$order = idor_find_order($realId, $sessionUid);
//   SELECT * FROM orders WHERE id = ? AND user_id = ?

// ③ 订单号不可枚举（纵深防御）
'ord_7f3a9c2e5b'                    // 而不是 1003

// ④ 越权时统一返回「不存在」
$error = '订单不存在。';
```

### 4.2 四层各自的角色

| 层 | 作用 | 是不是「必须」 |
|---|---|---|
| ① 身份来源 | 从服务端取，请求方改不了 | **必须** |
| ② 归属进查询 | 不存在「忘了判断」的可能 | **必须** |
| ③ 无法枚举 ID | 提高攻击成本 | 纵深防御 |
| ④ 不泄漏存在性 | 防止靠遍历枚举出有效 ID | 纵深防御 |

**①② 是必须的，③④ 是补充。** 这个区分很重要，因为
「只做 ③」是一种非常常见的错误修复 —— 下面单独说。

### 4.3 ⚠️ 最重要的一条：不可枚举 ID 不能替代权限校验

很多实现把「ID 换成 UUID / 随机串」当成越权的修复。**这是错的。**

```
?order_id=ord_b5c1e93d74   ← bob 订单的真实不可枚举 ID
                           → 仍然被拒绝（层 ② 生效）
```

本档的 CI 里专门有一条断言，用**真实的不枚举 ID** 去打 high 档，
确认它读不到。这条断言的意义在于排除一种错觉：

「用了随机 ID，所以不会有越权。」

**ID 会泄露。** 常见的泄露路径：

| 泄露路径 | 说明 |
|---|---|
| 分享链接 | 「把这条订单的链接发给客服」 |
| 浏览器历史 / 自动补全 | 多设备同步之后到处都是 |
| 服务端日志 / 访问日志 | 运维能看到，日志外泄时也带出去 |
| Referer 头 | 从订单页点到外部站点时带出去 |
| **接口响应** | 「订单列表」接口里就带着自己的订单 ID |
| 通知邮件 / 短信 | 「点击这里查看订单」 |

**一旦泄露，随机 ID 就退化成普通 ID。**

而权限校验不会因为「ID 被人知道了」而失效 ——
这就是为什么它是防线，而不可枚举只是成本。

### 4.4 层 ④：权限判断本身也会泄漏信息

如果越权时返回「无权访问」，攻击者就能区分：

```
无权限  → 这个订单存在
不存在  → 这个订单不存在
```

于是可以靠遍历枚举出「哪些 ID 是有效的」。

**所以本档把这两种情况合并成一句「订单不存在」。**

这是 Authorization 与 Information Disclosure 的交界 ——
**权限判断本身也是一个信息通道。**

类似的取舍在其他场景也出现过：登录失败时不区分「用户不存在」和「密码错误」
（防用户枚举）、SSRF 的错误信息不回显内网细节。

### 4.5 关于「所有接口都要过一遍授权清单」

越权最常见的成因不是「写错了」，而是**某个接口忘了写**。

所以除了修这一处，工程上还应该做一件事：
维护一份**显式的授权清单** —— 每个接口谁能访问、依据是什么。

这份清单的价值在于它是**可审查的**：
「这个接口需要什么权限」变成一个必须回答、且能对着代码核对的问题，
而不是「写代码的时候记得加」。

## 五、其他值得知道的手法

### 5.1 ID 之外的可控参数

越权不只看 ID。任何「客户端可以指定、而服务端不该相信」的参数都可能是入口：

| 参数类型 | 例子 | 危害 |
|---|---|---|
| 文件路径 | `?file=invoice_1001.pdf` | 读别人的发票 |
| 邮箱 / 手机号 | `?email=victim@x.com` | 触发对别人的操作 |
| 组织 / 租户 ID | `?tenant_id=999` | **跨租户越权（最严重的一类）** |
| 角色 / 权限字段 | 表单里多带一个 `role=admin` | 提权（Mass Assignment） |

**判断方法是一样的：这个参数在决定「访问什么」，而服务端的判断依据是「你是谁」——
那么「你是谁」必须来自服务端。**

### 5.2 垂直越权

水平是「A 看 B 的数据」，垂直是「普通用户干管理员的事」。

常见形态：

| 形态 | 说明 |
|---|---|
| 直接访问管理接口 | `/admin/users` 没做角色校验，只是前端不显示链接 |
| 改写请求 | 普通用户的请求里带 `role=admin`，服务端照单全收 |
| 接口版本差异 | `/api/v2/admin/...` 忘了复用 `/api/v1` 的权限中间件 |

**最典型的一种是「只在前端做了控制」**：
菜单不显示、按钮置灰、JS 里判断角色 —— 这些都是**用户体验**，不是安全边界。

检验方法：**把所有前端限制去掉，直接发请求。**
如果成功，那前端那层从来就不是防护。

### 5.3 上下文越权（业务逻辑越权）

这类最容易漏，因为它不是「访问了不该访问的对象」，而是「执行了不该允许的操作序列」：

| 例子 | 问题 |
|---|---|
| 优惠券反复使用 | 接口没检查「这个用户用过没有」 |
| 跳过审批步骤 | 直接调最终审批接口，不经过中间节点 |
| 超出业务上限 | 转账金额、下单数量只在**前端**限了最大值 |
| 状态机跳跃 | 从「已取消」直接改成「已完成」 |

**特点：每个单独的接口都是「正常」的，问题出在它们被调用的顺序和次数上。**
这类漏洞几乎没有工具能自动发现。

### 5.4 越权与 CSRF / XSS 的组合

| 组合 | 效果 |
|---|---|
| **越权 + CSRF** | CSRF 让受害者的浏览器发请求，越权让这个请求能改到别人的数据 |
| **越权 + XSS** | 越权接口返回的数据里如果含攻击者可控内容，就成了存储型 XSS 的投递点 |
| **越权 + IDOR** | 本身是同一件事的不同说法 |

本靶场的 burp 插件项目（`burp-idor-detector`）就是针对这类漏洞的检测工具 ——
它的核心是「**三态对比**」：基准请求 / 换身份重放 / **不存在的 ID 对照**。
第三步排除了同类工具最大的误报来源（把「正常的错误页」当成「越权成功」）。

## 六、防御清单

| 优先级 | 做法 | 说明 |
|---|---|---|
| **①** | **身份只来自服务端** | 会话 / 已校验的 token。**判据：这个值在不在请求里？** |
| **①** | **归属条件写进查询** | `WHERE id = ? AND user_id = ?`，而不是「查出来再用 if 判断」 |
| **①** | **默认拒绝** | 没有明确的授权规则 → 拒绝。而不是「没规则就放行」 |
| **①** | **维护授权清单** | 每个接口谁能访问、依据是什么。**清单本身可审查** |
| **②** | 越权时不泄漏存在性 | 统一返回「不存在」，把「无权」和「不存在」合并 |
| **②** | 不可枚举 ID | 提高成本，但**不能替代权限校验** |
| **②** | 用带签名的引用代替裸 ID | 例如一次性 token 形式的分享链接 |
| **③** | 前端控制 + 后端同时控制 | 前端那层是体验，后端那层才是边界 |
| **③** | 记录并监控越权尝试 | 正常用户不会访问别人的订单 —— 这种请求值得告警 |

按有效性排序：**① ≫ ② > ③**。

最后一条容易被忽略但很实用：
**越权请求在日志里是有特征的** ——
一个用户访问了不属于他的对象，这件事本身就是异常信号，
不管它是因为漏洞还是因为抓包工具。**值得单独告警。**

## 七、和本靶场其他场景的联系

### 7.1 靶场里最核心的一条主线

回到这一节反复出现的那个模式：

| 场景 | 防护依赖的信息 | 为什么不可靠 |
|---|---|---|
| SSRF | 输入里的字符串 | 同一个地址有无数种写法 |
| 命令注入 | 输入里的分隔符 | 黑名单列不全 |
| 反序列化 | 字符串里的类名 | 大小写不一致 |
| XXE | 请求体里的文本 | 实体声明可以在文档之外 |
| CSRF | `Referer` | 客户端可以自愿不发 |
| **JWT** | **`alg` 字段** | **算法由 token 自己声明** |
| **越权** | **`uid` 请求参数** | **身份由请求方自己声明** |

**七行里是同一句话：**

**防护所依据的那个信息，如果是请求方可以自由决定的，那它就挡不住请求方。**

反过来说：
CSRF token 有效，因为它由服务端生成；
会话身份可靠，因为它由服务端保存；
白名单可靠，因为它列举的是「允许什么」。

**「谁来决定这个值」——这是判断一条防护是否可靠的最短路径。**

### 7.2 与 JWT 场景的直接接续

两个场景在这里合上了：

```
JWT 场景   ：token 里的 role 字段能改吗？→ 能改 → 伪造 admin
越权场景   ：请求里的 uid 能改吗？     → 能改 → 读别人的订单
```

**两者是同一个错误的两种表现：把「请求方声明的身份」当成了「服务端确认的身份」。**

JWT 的正确用法（校验签名后读 `sub`）恰好就是越权场景的正确做法
（身份来自服务端校验过的来源）。**一个修好了，另一个也可以用同样的思路检查。**

### 7.3 与 burp-idor-detector 的关系

本靶场和那个 Burp 插件是配套的：

| | 靶场 | 插件 |
|---|---|---|
| 提供什么 | **确定的目标**（三档、行为已知） | **检测方法**（三态对比） |
| 怎么验证 | CI 断言守住三档行为 | 靶场提供「应命中 / 不应命中」的基准 |

插件的核心是**三态对比**：

```
① 基准请求      —— 用自己的身份访问自己的资源
② 换身份重放    —— 用 A 的身份访问 B 的资源
③ 不存在的 ID 对照 —— 用一个一定不存在的 ID 再试一次
```

**第 ③ 步排除了同类工具最大的误报来源**：
很多站点对不存在的 ID 也返回一个「正常的错误页」，
如果只比对 ① 和 ②，会把「错误页长得不一样」误判成越权。
拿一个不存在的 ID 做对照，就能确认「② 返回的内容确实是别人的数据」。

这和本靶场里反复出现的那条原则是同一个：
**负向对照 —— 排除「特征被检测行为本身制造出来」的可能。**
