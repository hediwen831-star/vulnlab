# 命令注入 Writeup

> 对应场景：`html/cmdi/low.php` / `medium.php` / `high.php`
>
> 本档所有载荷均经过实测（Windows + PHP 7.3 环境）。

---

## 一、原理：第四种「数据被当成代码」

前面三个场景已经建立了这个认知框架，命令注入是它的第四个投影：

| 场景 | 数据被当成 | 谁在解析 |
|---|---|---|
| SQL 注入 | SQL 语法 | 数据库 |
| XSS | HTML 语法 | 浏览器 |
| 文件上传 | 可执行文件 | Web 服务器 |
| **命令注入** | **shell 命令** | **操作系统** |

**危险的不是「用户输入了特殊字符」，而是「用户输入被 shell 解释了」。**

这句话需要精确理解。看 low 档的代码：

```php
$cmd = "ping -n 2 {$ip}";
shell_exec($cmd);
```

`shell_exec` 不是「执行一个叫 ping 的程序」——它是**把整个字符串交给系统 shell**
（Windows 是 `cmd.exe`，Linux 是 `sh`），由 shell 先解析再执行。

而 shell 的语法里，`&`、`|`、`;`（Unix）都是**命令分隔符**。
所以当 `$ip` 里含有这些符号时，shell 会把它理解为「命令结束，开始下一条命令」。

### 为什么它是最危险的一类

前三者还要绕一层：构造 SQL、构造标签、找到可访问路径。
命令注入**直接就是操作系统命令执行**：

```
一个 `& whoami`  →  确认身份
一个 & type C:\Windows\win.ini  →  读文件
一个反弹 shell   →  控制整台机器
```

**危害等级从「数据泄露」直接跳到「主机失陷」。**

## 二、low 档：零防护

### 2.1 利用

```
?ip=127.0.0.1 & whoami
```

页面会显示：

```
正在 Ping 127.0.0.1 具有 32 字节的数据:
请求超时。
...
52hz\hediwen        ← whoami 的输出
```

### 2.2 ⚠️ 平台差异（本档实测结论）

**不同 shell 的命令分隔符集合不一样。** 这是实测出来的：

| 分隔符 | Unix sh | Windows cmd | 说明 |
|---|---|---|---|
| `;` | 顺序执行 | **不是分隔符** | cmd 会把它当普通字符 |
| `&` | 后台执行 | **顺序执行（主分隔符）** | **两个平台都有效** |
| `\|` | 管道 | 管道 | 两个平台都有效 |
| `&&` | 逻辑与 | 逻辑与 | 前一条成功才执行后一条 |
| `\|\|` | 逻辑或 | 逻辑或 | 前一条失败才执行后一条 |
| 换行符 | 顺序执行 | **不是分隔符** | 只有 Unix 支持 |

**实测结果**（Windows）：

```
127.0.0.1 & whoami    → 注入成功，whoami 有回显     ✓
127.0.0.1 | whoami    → 注入成功                    ✓
127.0.0.1 && whoami   → 未执行 whoami（ping 失败，&& 短路了）
127.0.0.1; whoami     → 未执行 whoami（cmd 不认分号）
换行符                 → 不可用（cmd 不支持）
```

**所以「换行符绕过」这个在 Unix 上很经典的技巧，在 Windows 上完全无效。**
这类平台差异在 SSRF 场景也遇到过（IP 变形写法）—— 
**payload 的有效性永远依赖目标环境，不能照搬教程。**

### 2.3 关于 `&&` 的一个细节

`127.0.0.1 && whoami` 在目标 ping 不通时不会执行 `whoami` —— 因为 `&&` 是「前一条**成功**才执行后一条」。

想稳定执行用 `&`（无条件顺序执行）。

这个小细节在实战里很有用：探测时用 `&`，需要条件执行时才用 `&&`。

## 三、medium 档：黑名单与绕过

### 3.1 防护措施

```php
$blacklist = [';', '|', '$', '`', '>', '<'];

foreach ($blacklist as $bad) {
    if (strpos($ip, $bad) !== false) { /* 拦截 */ }
}
```

### 3.2 漏了什么

**漏了 `&`。**

```
?ip=127.0.0.1 & whoami      →  绕过成功，whoami 有回显
```

### 3.3 为什么这个漏项很真实

这不是我随手写的漏项，而是**真实世界里最常见的一种疏漏**：

开发者在 **Linux** 上开发、测试，脑子里想的是 Unix shell 的分隔符
（`;` `|` `` ` `` `$`），于是黑名单照这个思路写 ——
但**漏掉了 Windows cmd 最常用的 `&`**。

而 `&` 在 Unix 的 sh 里同样有效（作为后台执行符）——
所以这个漏项**在两个平台上都能被利用**。

真实项目里类似的情况还有：

- 只考虑 PHP，忘了 Web 服务器也会解析某些扩展名
- 只考虑 GET 参数，忘了 POST / Cookie / Header 里也能注入
- 只考虑 MySQL，忘了 PostgreSQL 的语法差异

**「按自己熟悉的平台写防护」是一个系统性风险，不是偶发失误。**

### 3.4 更根本的问题

即使把 `&` 也加进黑名单，还能用：

```
%25 变量展开（cmd 的 %VAR%）
^   转义字符（能构造出被过滤的字符）
( ) 命令分组
* ? 通配符展开（能读文件名）
```

**黑名单在原理上不可能完备** —— 因为 shell 的元字符集合是由 shell 的语法定义的，
而不同 shell 的语法还不一样（sh / bash / zsh / cmd / PowerShell 各有各的规则）。

这和 SQL 注入、XSS 的结论完全一致，只是换了一种语法而已。

### 3.5 顺带一提：本档的两个「意外收获」

开发这个场景时踩到两个真实的坑，都值得记：

**① PHP 的 `htmlspecialchars` 遇到非法 UTF-8 会返回空字符串**

Windows 上 `ping` 的输出是 **GBK 编码**（「正在 Ping ...」），
直接丢给 `htmlspecialchars()`（默认按 UTF-8 处理）会触发「非法 UTF-8 序列」，
而 PHP 在这种情况下**返回空字符串**，不是跳过非法字节。

表现是「命令输出那一栏莫名其妙是空的」，不报错、不告警。
修复要在 `htmlspecialchars` 里加 `ENT_SUBSTITUTE`，或者先把 GBK 转成 UTF-8。

> 有意思的是：我在 **XSS 场景的 high 档**里专门讲过「`ENT_SUBSTITUTE` 不能省，
> 否则构造的非法编码能让整个输出消失」—— 当时是从攻击者构造输入的角度讲的，
> 结果在这里以另一种方式真实踩到了。

**② 不能用 PHP 8 的函数**

high 档里我一开始用了 `str_starts_with()` —— 它是 **PHP 8.0 才引入**的，
而靶场声明兼容 PHP 7.2+，本机跑的是 7.3。

结果是 **Fatal error**，而页面上的表现是「那一块内容整体消失」，
很难第一时间联想到是函数不存在。

改用 `strpos($x, $prefix) === 0` 即可。

**教训：写兼容多版本的语言代码时，不要凭记忆用「看起来该有」的函数。**

## 四、high 档：两层修复

### 4.1 修复代码

```php
// ① 白名单校验：确认输入「长得像主机」
if (!looks_like_host($ip)) { /* 拒绝 */ }

// ② 参数转义：确保参数「不会被 shell 解释」
$safeIp = escapeshellarg($ip);
$cmd = "ping -n 2 {$safeIp}";
```

### 4.2 为什么两层都要

| 层 | 防的是什么 | 单独使用的风险 |
|---|---|---|
| ① 白名单 | 输入「是不是意外的东西」（业务层面） | 校验规则可能被绕过（解析差异、正则写漏） |
| ② 转义 | 「就算它是恶意的，也不能被执行」（语法层面） | 换命令构造方式时可能漏掉转义 |

**两层防的是不同方向的失败**，所以是叠加而不是二选一。

这和 SQL 注入的修复完全同构：

```
白名单校验  ≈  检查参数格式
参数化查询  ≈  让参数不参与语法解析
```

### 4.3 `escapeshellarg` 做了什么

它给参数加上引号，并把参数内部的引号转义掉：

```
输入:  127.0.0.1 & whoami
结果:  '127.0.0.1 & whoami'      （Windows 上是 "127.0.0.1 & whoami"）
```

这样 shell 会把整个引号内容当成**一个参数**，不会去解释里面的 `&`。

**注意：输入内容没有被修改** —— 只是它在 shell 里不再被当作语法。
这又是「让数据待在数据的位置上」这个原则的又一次体现。

### 4.4 更彻底的修复：不用 shell

```php
// PHP：参数以数组形式传给程序，完全绕开 shell
$process = proc_open(['ping', '-c', '2', $ip], $descriptors, $pipes);
```

```python
# Python
subprocess.run(['ping', '-c', '2', ip])        # 安全
subprocess.run(f'ping -c 2 {ip}', shell=True)  # 危险
```

```java
// Java
new ProcessBuilder("ping", "-c", "2", ip).start();
```

**「不经过 shell」和「参数化查询」是同一类修复**：
不是想办法把危险字符过滤掉，而是让危险内容**根本没有机会被解析**。

能选的话优先选这个 —— 它消除的是整类问题，而不是堵住某一个入口。

## 五、防御清单

```
✅ 首选「不经过 shell」：数组形式传参
   （PHP proc_open / Python subprocess list / Java ProcessBuilder）
✅ 必须用 shell 时，参数一律 escapeshellarg，不要自己写转义
✅ 白名单校验要有，但别当成唯一防线
✅ 能不用系统命令就不用 —— 很多场景有纯语言实现
   （IP 校验用 filter_var，根本不需要 ping）
✅ Web 进程降权运行（不能防注入，但能压小后果）

❌ 不要用黑名单过滤命令分隔符
❌ 不要以为「过滤了自己熟悉的平台的符号」就安全
❌ 不要把用户输入拼进命令字符串
❌ 不要以 root / Administrator 运行 Web 进程
```

### 关于「消除调用，就消除了注入面」

这一条值得单独说。

本档的场景是「ping 一个 IP」——但**校验一个 IP 需不需要真的 ping？**

```php
filter_var($ip, FILTER_VALIDATE_IP)   // 纯语言实现，零注入面
```

只有当业务真的需要「测试连通性」时才需要 ping。
很多真实项目里的命令注入，源头是「本来可以用库函数做的事，图省事调了系统命令」。

**最佳修复往往不是「把调用写安全」，而是「不调用」。**

## 六、四个场景的横向总结

到这里四个注入类场景全部完成。把它们放在一起：

| 场景 | 数据被当成 | 修复方向 | 共同原则 |
|---|---|---|---|
| SQL 注入 | SQL 语法 | 参数化查询 | 让数据不参与语法解析 |
| XSS | HTML 语法 | 输出编码 | 让数据不参与语法解析 |
| 文件上传 | 可执行文件 | 白名单+内容检查+禁执行 | 让可执行内容无法执行 |
| 命令注入 | shell 命令 | 数组传参 / escapeshellarg | 让数据不参与语法解析 |

**四者都是「数据进入了代码的位置」，区别只在解析器是谁。**

而防御思路完全一致：

> **不要试图过滤危险的东西，而是让危险的东西失去意义。**

- SQL → 参数化：危险内容永远只是「值」
- XSS → 输出编码：危险内容永远只是「文本」
- 上传 → 目录禁执行：危险内容永远不会被「执行」
- 命令 → 数组传参：危险内容永远不会被「解析」

**这条原则说四遍，才是这四个场景真正要教的东西。**
