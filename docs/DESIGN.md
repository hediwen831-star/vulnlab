# 设计文档：技术栈与教学设计

本文说明 VulnLab 的技术选型理由、漏洞场景的设计原理，以及它与现有靶场的差异。

---

## 一、技术栈

### 1.1 运行时

| 技术 | 版本 | 用在哪 | 为什么是它 |
|---|---|---|---|
| **PHP** | ≥ 7.2 | 全部后端 | 见 [3.1](#31-为什么用原生-php-而不是框架) |
| **SQLite** | 随 PHP 的 `pdo_sqlite` | 数据存储 | 见 [3.2](#32-为什么用-sqlite-而不是-mysql) |
| **PDO** | PHP 内置 | 数据库抽象层 | 统一 API，且预处理语句是修复注入的关键手段 |
| **PHP 内置服务器** | `php -S` | 本地运行 | 单进程即可跑，**零配置零依赖** |

### 1.2 前端

| 技术 | 用在哪 | 说明 |
|---|---|---|
| **原生 HTML + CSS** | 全部页面 | 无构建步骤，无 npm，clone 即可跑 |
| **CSS 自定义属性** | 主题变量 | `:root` 里定义配色，改一处全局生效 |
| **原生 PHP 模板片段** | `lib/layout.php` | 用函数输出 HTML，不引入模板引擎 |

不用前端框架的原因：靶场的页面总共不到 10 个，交互复杂度极低。
引入框架意味着引入 `node_modules`、构建步骤、版本管理，
而这只服务于「看起来更现代」这一个目的，却让「clone 下来能跑」变得脆弱。

样式上并未因此将就：页面用了完整的 CSS 变量体系、响应式栅格、语义化标签，
以及针对长 SQL 语句横向滚动的处理。

### 1.3 配套工具

| 工具 | 用途 |
|---|---|
| **Docker + Docker Compose** | 给没有 PHP 环境的人用的替代方案 |
| **Python 3（仅标准库）** | PoC 验证脚本 `poc_sqli.py`，零第三方依赖 |
| **YAML** | 机读 PoC 格式，可被扫描器引擎消费 |

## 三、关键设计决策

### 3.1 为什么用原生 PHP 而不是框架

框架自带的安全机制会掩盖漏洞本身。

Laravel 的 Eloquent ORM 默认参数化查询，ThinkPHP 有全局过滤，
在框架里写一个 SQL 注入场景**需要先想办法绕过框架的防护** ——
这时学生学到的是「怎么绕过 Laravel」，而不是「SQL 注入的成因是什么」。

用原生 PHP + PDO：

```php
// 危险写法（low.php）—— 拼接的恶意一目了然
$sql = "SELECT id, username, email, role FROM users WHERE id = $id";

// 安全写法（high.php）—— 占位符和数据分离
$sql = 'SELECT id, username, email, role FROM users WHERE id = :id';
$stmt = db()->prepare($sql);
$stmt->execute([':id' => (int) $id]);
```

两行代码并排放着，差异不需要解释，这正是教学需要的。

### 3.2 为什么用 SQLite 而不是 MySQL

| 维度 | MySQL | SQLite |
|---|---|---|
| 用户需要做什么 | 装服务、建库、导数据、配账号 | **什么都不用做** |
| 数据存放 | 独立服务进程 | 单个文件 |
| `php -S` 能否直接跑 | 否，还要起 MySQL | **是** |
| 教学效果 | 无差别 | 无差别（SQL 语法通用，注入手法一致） |

从 clone 下来到看到漏洞，应当只隔一条命令。

如果用户需要先装 MySQL、建数据库、跑建库脚本、改配置文件，
那么大概一半的人会在这一步放弃 —— 这跟靶场本身做得好不好没关系，
但会直接决定这个项目有没有人看。

数据文件放在 `html/data/vulnlab.db`，首次访问 `config.php` 时自动创建并灌入种子数据：

```php
if (!file_exists(DB_FILE)) {
    init_database();      // 建表 + 插入种子数据
}
```

**关于 MySQL 的说明**：项目预留了切换路径 ——
建表语句和查询语句都是标准 SQL，迁移到 MySQL 只需要改 DSN 和连接参数。
Docker 方案已提供，但默认走 SQLite。

### 3.3 为什么页面要直接显示执行的 SQL

这是本项目**最重要的教学设计**。

传统靶场的反馈循环是：
```
输入 payload → 看页面变化 → 猜服务端发生了什么 → 再试
```

VulnLab 的反馈循环是：
```
输入 payload → 页面显示「服务端实际执行的语句」→ 直接看到拼接结果 → 理解成因
```

medium 档更进一步，**并排显示「你的输入」与「过滤后」**：

```
你的输入    1' union select 1,username,secret,role from users-- 
过滤后     1'  1,username,secret,role  users-- 
              ↑ union 和 select 被删掉了，语句结构被破坏
```

学生能看到过滤器具体做了什么，而不是猜为什么打不通。
这把「试错」变成了「推理」。

### 3.4 为什么三档是三种不同性质的防护

很多靶场的「难度分级」只是「同一个漏洞，防护越来越严格」。VulnLab 设计成三种**不同性质**的防护：

| 档位 | 防护性质 | 注入点类型 | 打通需要理解什么 |
|---|---|---|---|
| `low` | 无 | 数字型（无引号） | 先判断「有没有引号」 |
| `medium` | 黑名单过滤 | 字符型（有引号） | 闭合引号 + 绕过黑名单 |
| `high` | 参数化查询 | 不可注入 | 为什么这样能根治 |

`medium` 档承载了其中一个关键知识点：黑名单在原理上必然失败。
理由不是防守方不够努力，而是：

```
黑名单的本质 = 枚举所有危险词
SQL 的表达方式 = 无穷的
```

只要存在两种表达同一语义的写法，黑名单就一定能被绕过。`medium` 档演示了其中一种：

```php
$blacklist = ['union', 'select', 'from', 'where'];
$filtered  = str_ireplace($blacklist, '', $id);
```

`str_ireplace` 是**单次非递归**替换 —— 它在原字符串上扫描匹配并删除，
**不会重新扫描删除后的结果**。这个特性产生了可利用的空间：

```
输入:      ununionion
扫描:      从索引 2 开始匹配到 "union"
删除后:    "un" + "ion"  =  union    ← 又变回危险词
```

同理 `seselectlect → select`、`frfromom → from`。

Writeup 里另外列了 5 种绕过思路（大小写混合、内联注释、URL 双重编码、
等价语法替换、十六进制字符串），每一种都对应「换一种表达同一语义的写法」。

### 3.5 为什么要有「已修复」档

只教「怎么打」的靶场，培养出的是只会说「这里有问题」的人。
真实环境下的差距在这里：

| 只会说问题 | 能说清修复 |
|---|---|
| 「这里存在 SQL 注入」 | 「这里是 SQL 注入，修复要用参数化查询，因为它把语句结构和数据分两次发送，参数永远只是值不参与语法解析。另外还应该加类型校验和错误信息收敛。」 |
| 追问「怎么修」就卡住 | 追问「为什么这么修有效」也能答 |

所以 `high.php` 是一个**功能完整但已修复**的版本，页面下方还做了对照实验：
把 low / medium 档成功的 payload 逐个列出来，展示它们在 high 档的结果
（全被类型校验拒绝）。

### 3.6 `source.php` 为什么要写得安全

靶场本身的代码不应存在漏洞，否则就成了「用漏洞来教安全」。

而「源码查看器」是任意文件读取漏洞的重灾区（真实世界里这类功能出事很常见）。
所以这里刻意写成了正确示范，用了三层防护：

```php
// 第 1 层：realpath 消解 —— 处理 ../ 与符号链接
$candidate = realpath($baseDir . DIRECTORY_SEPARATOR . $requested);

// 第 2 层：目录边界校验 —— 注意比较的是 realpath 之后的结果
if (strpos($normalizedTarget, $normalizedBase . '/') !== 0) {
    $error = '拒绝访问：目标文件不在允许的目录内。';
}

// 第 3 层：扩展名白名单（白名单优于黑名单）
if (!in_array($extension, ALLOWED_EXTENSIONS, true)) {
    $error = '拒绝访问：不支持查看该类型文件。';
}
```

**少任何一层都会出问题**，这个顺序也很重要：

- 只做第 2 层 → 符号链接可以绕过（因为 `../` 变形没被折叠）
- 只做第 1 层 → `../` 被消解了但没有边界检查，仍能读到目录外
- 只做第 3 层 → 后缀合法但目录不对，照样能读
- **顺序反了**（先做边界校验再做 realpath）→ 校验的是未折叠的路径，等于没校验

页面下方专门解释了这三点，把这个功能变成了第二个教学案例。

## 四、场景设计：以 SQL 注入为例

本章以 SQL 注入为例，展示一个场景的完整设计过程：数据表、三档的差别、
教学元素的取舍。其余 11 个场景遵循同一套结构，各自的技术细节见 `writeups/`
下对应的 Writeup。

**当前共 12 个场景**，每个都配齐四件套（三档源码 + Writeup + 机读 PoC + 修复对照）：

| 类别 | 场景 |
|---|---|
| 注入 | SQL 注入、命令注入、SSTI |
| 客户端 | XSS、CSRF |
| 文件 | 文件上传、文件包含（LFI）、XXE |
| 服务端请求 | SSRF |
| 反序列化 | PHP 对象注入（POP 链） |
| 身份认证 | JWT 签名绕过 |
| 访问控制 | 越权（IDOR） |

这些场景共享一条主线：防护所依据的那个信息，如果是请求方可以自由决定的，
那它就挡不住请求方。

| 场景 | 防护依赖的信息 | 为什么不可靠 |
|---|---|---|
| SQL 注入 | 删掉关键字后的文本 | 删除动作把片段拼了回来 |
| 文件包含 | 删掉 `../` 后的路径 | 同上 |
| 反序列化 | 字符串里的类名 | PHP 找类时不区分大小写 |
| XXE | 请求体里的文本 | 文档 + 外部 DTD 才是解析器实际的输入 |
| JWT | `alg` 字段 | 算法由 token 自己声明 |
| CSRF | `Referer` | 客户端可以自愿不发，域名也可以自愿包含 |
| SSTI | 括号 | 反引号运算符不需要括号 |
| 越权 | `uid` 请求参数 | 身份由请求方自己声明 |

### 4.1 数据表设计

```sql
CREATE TABLE users (
    id       INTEGER PRIMARY KEY,
    username VARCHAR(64)  NOT NULL,
    password VARCHAR(128) NOT NULL,   -- 存 MD5，靶场里的假数据
    email    VARCHAR(128) NOT NULL,
    role     VARCHAR(32)  NOT NULL,
    secret   TEXT         NOT NULL    -- 通关凭证：只有注入才能读到
);
```

**关键的列可见性设计**：

低/中档的查询是：

```sql
SELECT id, username, email, role FROM users WHERE id = ...
```

**故意不含 `secret` 列**。这意味着：

- 正常查询永远拿不到 `secret` —— 必须改变语句结构才能读到
- 想读 `secret` 必须用 UNION 注入，把 `secret` 塞进回显列的位置

这样就避免了「页面本身就显示了 secret，学生不知道自己打没打通」的问题。

### 4.2 种子数据

| id | username | role | secret |
|---|---|---|---|
| 1 | admin | admin | `VULNLAB{union_select_master}` |
| 2 | alice | user | `nothing-here-for-alice` |
| 3 | bob | user | `nothing-here-for-bob` |
| 4 | carol | auditor | `nothing-here-for-carol` |
| 5 | dave | user | `nothing-here-for-dave` |

只有 admin 有真实凭证，其他都是干扰项。
`role` 列有 `auditor` 这种非标准值，增加枚举时的信息量。

**全部是假数据**，密码是常见弱口令的 MD5（如 `5f4dcc3b...` 是 `password`），
既是彩蛋也是「弱口令」这个知识点的暗示。

### 4.3 错误回显的取舍

低/中档**故意显示数据库错误信息**：

```
SQLSTATE[HY000]: General error: 1 near "''": syntax error
```

这是刻意的。报错回显是 SQL 注入检测与利用的重要信息来源：

- **检测**：注入一个单引号看是否报错，是判断注入点最快的方法
- **利用**：报错型注入靠的就是把数据塞进错误信息里

而 `high` 档**关闭了错误回显**，只返回「查询失败，请稍后重试」，
并在页面说明了原因：报错信息会泄漏表名、列名、数据库版本，
是攻击者构造 payload 的重要依据。

同一个项目里演示「该显示」和「不该显示」，对比才有意义。

## 五、与现有靶场的差异

本项目不声称「首创」。DVWA、bWAPP、OWASP juice-shop 都是成熟且优秀的靶场项目，
本项目在场景覆盖度上远不及它们，差异在教学方式上。

| 维度 | 常见做法 | VulnLab 的做法 |
|---|---|---|
| 源码可见性 | 需要自己去翻仓库 | 页面右上角一键查看当前页源码 |
| 执行反馈 | 只有输入框和输出 | **页面直接贴出服务端执行的 SQL** |
| 过滤器可见性 | 只能靠猜 | 并排显示「你的输入」与「过滤后」 |
| 修复教学 | 通常没有 | 每档配修复对照 + 对照实验表 |
| 自动化 | 通常没有 | 每个场景配**机读 PoC**，可被扫描器消费 |
| 启动成本 | 需要 Web 服务器 + 数据库 | **`php -S` 一条命令**，SQLite 自动建库 |

最后一项（机读 PoC）是与其它靶场差异最明显的一点，
它让靶场从「给人练的靶子」变成了「**给工具测的基准**」：

```bash
# 扫描器引擎可以直接消费这些 PoC 来验证自身效果
python -m asp.cli poc run http://127.0.0.1:8080 --dir ../vulnlab/pocs
```

而 `high` 档（已修复）构成了天然的**误报诱饵**：
扫描器若在这里报漏洞，说明它的判定逻辑有问题。

搜索验证（GitHub API，2026-09）：
`vulnerable application benchmark scanner` → **0 个结果**。
这个组合确实很少有人做。

## 六、已知局限

诚实列出做不到的地方：

| 局限 | 说明 |
|---|---|
| **场景深度而非广度** | 12 个场景覆盖 OWASP Top 10 的主要类别，但每个只到「可复现 + 可绕过 + 可修复」这一层，不做真实业务逻辑的复杂度（如多步支付、权限继承链） |
| **无多用户/计分** | 没有账号体系、没有进度记录、没有 flag 提交系统 |
| **SQLite 非生产形态** | 虽然 SQL 语法通用，但 MySQL 特有的注入手法（如宽字节注入）无法演示 |
| **PHP 7.3 兼容代价** | 为了兼容旧环境（CI 矩阵的最低版本），没用 PHP 8 的 `match`、命名参数、`str_contains` 等特性 |
| **不做容器编排之外的自动化** | 有 CI 做安全属性回归，但没有自动部署到公网环境 —— 使用者需要自己起服务 |

### 关于「CI 自动化验证」——这一条已经补上了

早期版本这里写的是「没有 CI 去验证每个场景确实可被打通」，并把它列为
「最值得补的一项」。现在它已经完成：

- `tests/verify_lab.py`，**78 条断言**，覆盖 12 个场景
- 每个场景三类断言：**漏洞档确实能打通 / 绕过档确实能绕过 / 修复档确实打不动**
- 修复档还额外配一条「**功能未被误伤**」的反向保护 ——
  防止把「修好了」做成「改成不能用了」
- 在 PHP 7.3 / 7.4 / 8.1 三版本矩阵下跑，保证行为一致

**但配了 CI 不等于判据是对的。** 这条经验值得单独记一笔：

CI 断言用的是「**文件系统状态**」这类确定性判据（比如直接检查
探针文件有没有落盘），而机读 PoC 用的是「**页面文案**」。
两套载荷、两套判据 —— 改了其中一边，另一边不会跟着变。

实际踩到的例子：反序列化场景的页面判据依赖「目录里出现了新文件」，
而 POP 链写文件是覆盖式的 —— 同一个 payload 跑第二次就不报成功了。
后果是机读 PoC 变成**一次性**的（第一次命中，之后永远零命中），
而 78 条 CI 断言**全部通过** —— 因为断言跑前会先清理探针文件，
每次都制造出「首次写入」的条件，恰好绕开了这个缺陷。

判据被测试夹具自己清理干净，缺陷也就被掩盖了。所以「重复执行两次」
这类断言是必要的：幂等性缺陷只有跑第二遍才暴露。

现已补上 3 条专门的幂等性断言（`check_unserialize_*_idempotent`）。
