# 实验章节草稿：误报的可分解性与降噪的边界

> 说明：这是可并入论文的实验章节初稿，数字全部对应当前仓库
> （vulnlab 基准 91 例、attack-surface v0.1.2）。写作时保持「口径先于结论」的顺序：
> 先交代分母和判定规则，再给结果，避免读者用自己的口径去套。

## 1. 研究问题

本文不试图证明「某个扫描器更强」，而是回答三个可证伪的问题：

**RQ1** 扫描器的误报能否按成因拆解，而不是笼统地报一个「误报率」？
**RQ2** 在判据正确的前提下，误报率能做到多低？误报与漏检是否独立？
**RQ3** 引入 LLM 复核，收益与代价各是多少？它能不能直接替代判据？

三个问题对应三组实验：分层评测（M2）、判据对照（M2 的 PoC 覆盖实验）、
降噪量化（M4）。

## 2. 基准构建

### 2.1 为什么自建

公开靶场（DVWA、sqli-labs 等）提供漏洞页面，但不提供**真负例**：
它们没有「功能完整但已修复」的对照实现。缺少真负例，误报率只能靠人工判，
无法复现。本文的基准以「场景 × 档位」为单元：

| 档位 | 语义 | 预期结论 |
|---|---|---|
| low | 未防护 | 可被检出（正例） |
| medium | 有防护但可绕过 | 可被检出（正例） |
| high | 已修复，功能不变 | 不可被检出（负例） |

13 个场景 × 3 档 = 39 条基础用例，其中 26 条正例、13 条负例。

### 2.2 负例的扩充：绕过尝试

13 条负例的统计效力不足：一个样本值就是 7.7 个百分点，0/13 的 95% 置信区间
上限约 22.8%，无法支撑「误报率接近 0」的结论。为此给每个 high 档补 4 条
**绕过尝试**，负例扩到 65 条。四条变体固定对应四类手法：

| 变体 | 手法 | 典型构造 |
|---|---|---|
| 1 | 原始载荷复放 | 在 low 档成功的 UNION / `<script>` / `; id` 直接打到 high |
| 2 | 等价写法 | `localhost` 代 `127.0.0.1`、`1 OR 1=1`、管道符代替分号 |
| 3 | 编码或语法变形 | 反引号、换行、`php://filter`、双扩展名、`alg=none` |
| 4 | 边界值或链式 | 负值、数组参数、十进制 IP、`file://`、外部 DTD |

分类口径对齐 OWASP WSTG 与 PayloadsAllTheThings，每条记录手法、依据与参考来源。
**正例保持 26 条不变**：扩负例是为了压窄 FPR 的区间，TPR 的 26 个样本
给出 87%–100% 的区间，足以支撑方法可行性的论证。

### 2.3 真值的持续守护

基准本身会腐化：页面改版、修复逻辑被改坏，清单却还在。为此把每条真值钉在断言上：

- `tests/verify_lab.py`：89 条基础安全属性断言（正例可检出、负例打不动）
- `tests/verify_negatives.py`：52 条绕过变体逐条重放，52/52 通过
- `tests/verify_benchmark.py`：清单与源码、断言、PoC 的静态一致性校验

三项都在 CI 中执行。断言红即真值失效，评测结果自动作废。

## 3. 指标与口径

对被测工具 $T$、用例集合 $C$，记 $V$ 为正例集（26）、$S$ 为负例集（65）：

$$
TPR=\frac{|TP|}{|V|},\qquad FPR=\frac{|FP|}{|S|}
$$

分项误报率按成因拆解：

$$
FPR_c=\frac{|\{x\in FP \mid cause(x)=c\}|}{|S_c|}
$$

其中 $S_c$ 是负例中带有成因标签 $c$ 的用例数（一条用例可带多个标签）。

四条口径必须同时交代，否则数字不可比：

1. **FPR 的分母固定为全部 65 条负例。** 没报出来就是没误报；没去尝试是覆盖问题。
   报告另列「尝试用例数」，只展示、不进分母，避免奖励「少测少错」。
2. **归属三级优先**：规则里的 case id → 查询参数精确匹配 → 路径（落到基础用例）。
   同一页面挂 5 条用例时，只按路径归属会把误报算错地方。
3. **区间必报**。所有比率给 Wilson 95% 区间；0/65 的上限是 5.6%。
4. **降噪要报代价**：$\Delta FPR$ 与 $\Delta TPR$ 同时给，并列出被剔除的具体用例。

## 4. 实验设置

| 项 | 配置 |
|---|---|
| 靶场 | PHP 7.3 内置服务器，`127.0.0.1:8080`（主站）+ `:8090`（模拟内网） |
| 被测工具 | `probe`（判据上限）、`asp`（自研引擎，16 个 YAML PoC）、`naive`（只查载荷反射的基线） |
| 复核模型 | DeepSeek `deepseek-chat`，temperature=0，每轮独立 |
| 轮次 | 评测 1 轮；降噪 3 轮，比较每轮剔除集合是否一致 |
| 环境 | Windows 10，Python 3.13，单机回环，无外部网络依赖 |

## 5. 结果

### 5.1 主结果

| 工具 | TPR | FPR | 尝试覆盖 |
|---|---:|---:|---:|
| probe | 100.0%（26/26） | 0.0%（0/65） | 16/91 |
| asp | 100.0%（26/26） | 0.0%（0/65） | 未上报 |
| naive | 30.8%（8/26） | 12.3%（8/65） | 91/91 |

对 RQ1 的回答是分项表：

| 成因 | 负例数 | probe | asp | naive |
|---|---:|---:|---:|---:|
| 身份依赖 | 15 | 0 | 0 | 0 |
| 有状态副作用 | 15 | 0 | 0 | 6.7%（1/15） |
| 特征自污染 | 35 | 0 | 0 | 20.0%（7/35） |

naive 的误报高度集中在「特征自污染」：它把「响应里出现载荷标记」当成漏洞证据，
而 high 档页面会把输入回填进表单。8 条误报里有 7 条属于这一类，
其中 4 条来自新加的绕过变体 —— 变体越多，这类判据的缺陷越藏不住。

### 5.2 误报与漏检的独立性

旧基准上做过一次对照：`asp` 漏掉的两档恰好是唯一没有 PoC 的两个用例。
只补这两个 PoC、其它条件不变，TPR 从 92.3% 提到 100%，FPR 保持 0。
据此可以说：**检出率的上限由 PoC 覆盖率决定，与误报率无关**。
这条结论在小样本上成立，扩到 65 条负例后未被推翻（当前 asp 已是全 PoC 覆盖）。

### 5.3 降噪的收益与代价

| 扫描器 | 复核 | TPR | FPR | 剔除/轮 |
|---|---|---|---:|---:|
| naive | 启发式 | 30.8% → 30.8% | 12.3% → 12.3% | 0 |
| naive | DeepSeek | 30.8% → 30.8% | **12.3% → 4.6%** | 5 |
| asp | DeepSeek | **100% → 92.3%** | 0% → 0% | 3 |

三点观察：

其一，启发式降级完全无效。它只认错误页特征，而本基准的误报页全是 200 正常页。

其二，LLM 在「有误报可降」时表现良好：摘掉 5/8 条误报，未误杀任何真命中。
剩下的 3 条（`xss-high` 两条、`unserialize-high` 一条）都是「转义后的文本」与
「序列化串回显」，纯文本判断不出可执行性，需要在判据层解决。

其三，在「无误报可降」时，LLM 只会造成损失：`asp` 的 FPR 已经为 0，
复核却砍掉 3 条真命中（2 条 SSTI、1 条反序列化），TPR 掉 7.7 个百分点。

这解释了为什么工程实现把复核结论定位为**标注**而不是删除动作：
误杀的代价是不可逆的漏检，而多留几条待复核项只是增加人工成本。

### 5.4 外部引擎接入（受限比较）

用 24 个自写模板（12 low + 12 medium）把 Nuclei 接进同一套指标：

| 工具 | TPR | FPR | 命中 | 未归属 |
|---|---:|---:|---:|---:|
| Nuclei（24 模板） | 92.3%（24/26） | 0.0%（0/65） | 24 | 0 |

漏的两条是 SSTI。`{{ }}` 与 Nuclei 的模板变量语法冲突，用编码技巧拼出的花括号
会被二次求值，实际发出的是求值结果，判据退化为「响应里有回显」。
第一版模板曾「命中」，dump 请求体后确认是假阳性，已删除。

这个结果只能读作「模板覆盖了 24 个正例」，不能读作「Nuclei 的检出率是 92.3%」：
65 条负例没有被模板覆盖，而且模板由靶场作者编写，天然知道打哪里、匹配什么。

因此本节只用于回答一个工程问题：**同一套真值能否接纳外部引擎的输出**。
答案是能 —— 适配器把 JSONL 归一成统一结构，13 条命中全部正确归属，
零未归属。横向能力比较需要一份独立的、预先注册的模板集，列为后续工作。

### 5.5 统计强度

naive 的误报从 8 条降到 3 条，McNemar 精确检验双侧 $p=0.0625$，未过 0.05。
方向明确、机理清楚，但样本量不足以宣称统计显著。这一点在讨论中如实标注，
不把「有效」写成「显著」。

## 6. 讨论

**误报是可分解的。** 把误报按「判据为什么错」归类后，不同工具的失败模式差异明显：
naive 全部落在特征自污染，asp 与 probe 为零。笼统的「误报率 12%」既不能指导修复，
也不能比较工具。

**判据与模型的分工是清楚的。** 判据负责「能不能确定」，模型负责「确定不了时怎么判」。
把模型放在全量兜底的位置，既贵又危险 —— 5.3 的第三点就是证据。

**基准的规模决定结论的强度。** 同一套判据、同一个工具，负例从 13 条扩到 65 条，
FPR 的区间上限从 22.8% 压到 5.6%。这不是工具变好了，是测量变准了。

## 7. 效度威胁

| 类型 | 威胁 | 应对 |
|---|---|---|
| 内部 | 靶场与判据由同一作者实现，可能存在「按靶场写判据」的偏置 | 判据只用通用特征；负例变体覆盖四类通用手法；CI 独立重放 |
| 构念 | 用回环环境代表真实目标，缺少网络抖动与 WAF | 明确限定「应用层判据评测」，不外推到实战误报率 |
| 外部 | 单模型、单温度、单语言运行时 | 论文中限定结论范围；跨模型对比列为后续工作 |
| 结论 | 误报样本仅 8 条，McNemar 不显著 | 报告区间与 p 值，不使用「显著改善」的措辞 |
| 测量 | 部分工具不逐条尝试用例，FPR 分母可能高估其覆盖面 | 单列「尝试覆盖」，并在讨论中说明 |

## 8. 可复现性

```bash
# 起靶场
php -S 127.0.0.1:8080 -t html &
php -S 127.0.0.1:8090 -t html &

# 真值校验（89 + 52 条）
python tests/verify_lab.py --url http://127.0.0.1:8080
python tests/verify_negatives.py --url http://127.0.0.1:8080

# 主实验
python benchmark/harness/evaluate.py --scanner probe --url http://127.0.0.1:8080
python benchmark/harness/evaluate.py --scanner naive --url http://127.0.0.1:8080
python benchmark/harness/evaluate.py --scanner asp --url http://127.0.0.1:8080 \
    --asp-repo ../attack-surface

# 降噪实验
ASP_LLM_API_KEY=... python benchmark/harness/denoise.py --scanner naive \
    --url http://127.0.0.1:8080 --provider openai --rounds 3
```

原始数据与报告：`benchmark/results/`（当前口径）与 `benchmark/results/archive/n13/`
（旧口径，仅追溯）。每个数字都能在对应的 JSON 里找到逐条命中记录。
